# 2026-10-12 PLC 핸드쉐이크 수정 계획

PLC 담당자 회신([[PLC 핸드쉐이크 확인 질문지]])을 반영한 Vision 측 수정 계획입니다. 회신으로 Start·Ready·Initialize·결과 읽기 계약은 확정됐습니다. Move 정지 사건의 첫 단계는 회신과 로그가 서로 맞지 않아 PLC 재확인이 필요합니다. 소스는 아직 변경하지 않았습니다.

## 1. PLC 회신 요약과 Vision 영향

| 항목 | PLC 회신 | Vision 현재 | 조치 |
| --- | --- | --- | --- |
| 신호 맵 | 주소 일치. Auto·Manual·InitScanPos·End·Stop 미사용. InitScanPos는 OFF여야 운전 가능 | 일치. 미사용 비트는 켜지 않음 | 워드 보존 수정 후에도 미사용 비트는 항상 0 유지 |
| M1·M2·M3 | RESP_Move는 REQ_Move ON이면 ON, OFF면 OFF. 레벨 | 레벨 처리 가정과 일치 | Move 대기 상태기계를 레벨 기준으로 정리 |
| M4 | 응답 없이 다음 Start로 가는 경로는 IWS(Vision)가 확인할 것 | — | 아래 2절 로그 근거로 재확인 요청 |
| M5 | (응답 전 OFF 후 재 ON은) PLC에서 무시 | 사건에서 RESP_Start 쓰기가 REQ_Move를 지운 뒤 재 ON → 142 s, 24.5 s 무응답 | 비트 덮어쓰기 수정이 정지 원인 제거의 핵심. "무시"의 정확한 의미는 재확인 |

| R3 | 두 카메라 결과 판단은 IWS가 할 것 | 로그상 두 카메라 값이 어긋난 사이클 0건 (사실상 합산값) | 두 카메라 중 하나라도 NG면 2로 명시 |
| R5 | 최대 170 ms 지연 허용 | — | 완료 장벽 적용 |
| L1·L2 | Ready는 검사 시작 전 1회 확인. 항상 ON이어도 됨 | LinkTest가 Ready를 지움 | 워드 보존 수정으로 Ready 항상 ON |
| L3 | RESP_Initialize는 REQ_Initialize OFF 시 OFF | OFF 코드 주석 처리 | REQ OFF 확인 시 RESP OFF |

| PLC 정보 | Q 시리즈, 스캔 15 ms, MC 접속 4개, 비트 단위 쓰기 "?" | — | 비트 쓰기 대신 워드 보존 방식 유지 |

## 2. 회신과 로그가 맞지 않는 점 (사건 1)

PLC 회신대로라면 RESP_Move는 REQ_Move를 그대로 따르고, Move 응답 없이 다음 Start로 가는 경로는 없습니다. 그런데 08-25 로그(Seq 1579)에서는 다음 순서가 기록됐습니다.

| 시각 | 내용 |
| --- | --- |
| 09:40:42.693 | Vision REQ_Insp_Move ON 쓰기 완료 (D30201 = 0x0010) |
| 09:40:42.819 | REQ_Insp_Start OFF 관측. RESP_Insp_Move는 OFF |
| 42.819 ~ 43.134 | 약 300 ms 동안 폴링. RESP_Insp_Move는 한 번도 ON으로 관측되지 않음 |
| 09:40:43.134 | PLC가 다음 REQ_Insp_Start ON (Seq 1580, Div 2) |
| 09:40:43.180 | Vision이 RESP_Insp_Start ON을 쓰면서 D30201 = 0x0002. 이때 처음으로 REQ_Move 비트가 0이 됨 |

Vision은 42.693부터 43.180까지 D30201에 아무것도 쓰지 않았습니다. 검사 스레드는 D30210·D30211·D31000~만 씁니다. 따라서 이 구간에 PLC가 본 REQ_Move는 계속 ON이었는데, PLC는 RESP_Move를 켜지 않고 다음 Start를 올렸습니다. 이 부분은 래더에서 확인해야 합니다. 4번째 MC 접속 같은 다른 클라이언트가 D30200~D30201에 쓰는지도 함께 확인해야 합니다.

이후 142초 정지는 Vision 결함(RESP_Start 쓰기가 REQ_Move를 지움)과 PLC의 "재 ON 무시"(M5)가 겹쳐 생긴 것으로 보입니다. 워드 보존 수정만으로 이 2단계 정지는 막을 수 있습니다. 1단계(응답 없이 다음 Start)는 Vision 수정으로 막을 수 없고, timeout과 알람으로 드러나게 하는 것이 Vision이 할 수 있는 최선입니다.

## 5. PLC 재확인 질문

1. **사건 1 (2절)**: 09:40:42.693~43.180 동안 D30201.4가 ON이었는데 RESP_Move 없이 다음 Start가 나온 이유. 이 구간 래더 모니터나 이력이 없으면 재현 시 D30201·D30301을 트레이스해 달라고 요청. 다른 MC 클라이언트가 D30200~D30201에 쓰는지도 확인.
2. **M5 "무시"의 의미**: 응답 전 REQ_Move OFF를 무시하는 것인지, 이후 재 ON을 무시하는 것인지. 그 뒤 PLC 시퀀스 상태와 복구 방법.
3. **M7 재시도**: M5와 함께 볼 때 재시도가 실제로 받아들여지는지. 허용 대기 시간.
4. **ALARM(D30200.4)**: ON일 때 PLC 동작(정지, 경고만, NG 배출), 해제 조건(Vision OFF, RESET 스위치).
5. **InspRet 0**: 쿠폰 점검(Job 4)에서 InspRet 0인데 진행된 이유. 빈 결과를 2(NG)로 보내도 되는지.
6. **L4 5 s 기준점**: REQ_Initialize ON부터 RESP_Initialize ON까지인지.
7. **RESP_TimeSync**: PLC가 REQ_TimeSync를 내는 조건(평상시 없음이라고 했으므로 어떤 경우인지).

## 6. 검증 계획

1. 단계별 `HubisVIS.sln` Debug|x64 빌드, 경고·오류 확인, 편집 파일 한글 깨짐(U+FFFD) 확인.
2. 오프라인: P15.1 VirtualPLC로 정상 사이클과 fault injection(Move 무응답, REQ_Start 미해제, 빈 결과, 스캔 실패, Initialize 장시간 유지)을 확인. 각 경우 PLC 쪽에서 보이는 D30200·D30201 워드 값을 로그로 확인.
3. 현장 HIL은 별도 승인 후 진행. 첫 운전은 기존 `[PLC_START_DIAG]`·`[PLC_MOVE_DIAG]` 로그로 정상 사이클 타이밍(Start 응답, Move 응답 177 ms 이내, 사이클 시간 증가 170 ms 이내)을 비교.
4. 배포 시 AlgorithmTools DLL과 이를 쓰는 실행 파일을 같은 산출물 세트로 교체.
